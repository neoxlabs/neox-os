# 这些代码在 Linux 体系里处在哪一层 · 以及怎么变成镜像

> 2026-08-14

---

## 1. 现在的代码属于什么

**一行内核态代码都没有。全部是用户态（ring 3）。**

具体位置是**系统服务层** —— 跟 systemd、dockerd、Android 的 SystemServer 同一层。

```
        硬件 (AGX / x86 服务器)
────────────────────────────────────────────
  Linux 内核 (ring 0)          ← 不写, 只配置
  ├─ namespace / cgroup2
  ├─ landlock / seccomp / LSM
  └─ eBPF 挂载点               ← 将来会往这里放程序, 现在没有
────────────────────────────────────────────
  用户态 (ring 3)
  ├─ neox-init   PID 1 / 进程表 / 事件日志 / 决策   ← 我写的
  ├─ neox-engine 页表 / 组装 / 连接池              ← 我写的
  ├─ 约束启动器  unshare → cgexec → landlock-run   ← confine 生成的命令行
  └─ agent 执行体 被内核约束的普通进程
```

**但要诚实**：这些代码**至今没有以系统服务的身份运行过**。
现在它是一个跑在 macOS 上的 node workspace，53 个测试全绿 ——
设计成系统服务层，还没当过系统服务。

### 用 Android 对照（最贴切的类比）

| Android | Neox OS | 状态 |
|---|---|---|
| Linux kernel | Linux kernel | 不动 |
| init (PID 1) | `neox-boot` | ✅ 写了，没在 Linux 上跑过 |
| zygote（预热进程，fork 出 app） | `engine` 的页表 fork | ✅ 写了，实测 2µs |
| SystemServer（系统服务集合） | `neox-init` | ✅ 写了 |
| Binder（IPC） | NeoxABI | ⚠️ **还是同进程函数调用，不是真 IPC** |
| PackageManager / 权限 | `confine` + Capability | ⚠️ 纯函数写好，内核路径没验过 |
| ART（跑 app 的运行时） | agent loop 引擎 | ⬜ 还没搬过来 |
| App | agent 执行体 | ✅ 骨架有 |

**结论：我们在做的正是"澎湃 OS 那一层"** —— 内核用 Linux，个性层自己写。

## 2. 除了内核，什么都能动 —— 但内核也不是完全不能动

三个层次要分清：

| 层次 | 能不能动 | 怎么动 |
|---|---|---|
| 内核**源码** | 不动 | 改了就要自己维护，且失去上游安全更新 |
| 内核**配置** | 能动 | 开 `CONFIG_BPF_LSM` / `CONFIG_CHECKPOINT_RESTORE` / `CONFIG_DEBUG_INFO_BTF`。AGX 上大概率**必须**自编内核 |
| 内核**行为** | 能动 | eBPF / LSM 程序。**这是"改内核行为但不改内核代码"的正路** |
| 用户态全部 | 随便动 | 就是我们的地盘 |

所以"自己的 OS"落在：**内核配置 + eBPF 个性层 + 用户态系统服务**。

## 3. 三种交付形态（按难度递增，共用同一份 rootfs 定义）

### 形态 A · 容器镜像（先做这个）
```
docker run neox-os:latest    # 装在任何现成 Linux 服务器上
```
- 最容易，`Dockerfile` 已写（**还没构建过**）
- 用来验证一切：自检、confined 启动、landlock 是否真拦得住
- 局限：容器共享宿主内核，`CONFIG_*` 由宿主决定

### 形态 B · 系统镜像（真正的"装一个 OS"）
```
neox-os-<ver>.img → dd 到盘 / 云上导入 → 开机即是 Neox OS
```
- 基于 Ubuntu，用 `mkosi` / `debos` 构建
- AGX 上是：flash L4T + 我们的 rootfs 叠加（内核可能要自编）
- **跟形态 A 共用同一份包列表和 neox-init**，只是打包方式不同

### 形态 C · 安装器
- 最重，最后做，且只有在要卖硬件时才需要

**顺序：A 验证 → B 交付 → C 看情况。**

## 4. 端侧怎么接：ESP32 / 手机 / Android 都是同一条路

这是前面那条设计的红利 —— **UI 只是订阅者之一，没有特权客户端**。

任何设备只要能做两件事，就是一个合格的管家终端：

```
① 订阅事件流       ← log.subscribe / subscribeAll
② 回一个决策       ← decide.resolve(did, choice, by)
```

于是：

| 设备 | 需要实现什么 | 大小 |
|---|---|---|
| **ESP32** | 一条 WebSocket/MQTT + 只渲染 `choice`/`approve` 两种 PresentSpec（一块屏 + 两个按钮） | 极小 |
| **Android**（你先跑这个） | 全套 PresentSpec 渲染 + 事件流 | 中 |
| 网页 | 同 Android | 中 |
| 桌面 | 同上 + 高带宽视图 | 大 |

**关键点：`PresentSpec` 是语义的不是像素的**，所以 ESP32 只实现两种 kind 也能工作 ——
它收到 `form` 时可以直接说"这个我显示不了，去手机上处理"，而不是崩掉。

这也是为什么我把呈现协议做成白名单封闭的：**能力下限由最小的那个设备决定，
但小设备不会拖累大设备。**

## 5. "大概率还是 agent loop" —— 对，但每一环都被 OS 放大

你这个判断是对的。ReAct 不会消失，变的是每一环的成本和上限：

| loop 的环节 | 现在 | 有了 OS 之后 |
|---|---|---|
| 起子任务 | 新运行时，几百 ms | fork 执行体，~2µs，共享前缀 |
| 组 prompt | 各处各自组，缓存易废 | 单一组装器，父字节恒为子前缀 |
| 调工具 | 只能用包装过的 | 任何 Linux 程序，内核兜底 |
| 拿结果 | 大结果走两遍 JSON | 传引用 |
| 记忆 | 压缩即丢失 | 换出到 swap，可取回 |
| 等待 | 占着运行时 | `waiting` 不计资源，可换出 |
| 要人拍板 | 卡住等当前 UI | 登记决策，任意设备任意时刻回 |

**loop 是策略（我们的 IP），OS 是它的执行基础设施。** 两者不冲突。

## 6. 验证顺序（必须先验再往上盖）

| # | 验什么 | 成功判据 | 依赖 |
|---|---|---|---|
| **V0** | plan 收敛成唯一制品 | `capabilityAllows` 这个函数消失，交叉验证测试退化成 plan 性质测试 | 无 |
| **V1** | 容器镜像能构建、能启动 | `docker run` 后自检打印 ✓，PID 1 是 neox-init | Linux + docker |
| **V2** | **landlock 真的拦得住** | 授 `read:/in` 的进程读 `/etc/passwd` 拿到 EACCES；不授就连不上网 | V1 |
| **V3** | 安卓端收到一条决策并回复 | 手机上点一下，服务器上的进程继续跑完 | V1 + 一个最小客户端 |
| V4 | AGX 内核体检 | 四项 CONFIG 齐不齐；缺了就知道要不要自编内核 | 有机器 |

**V2 是这套东西的第一个真正证明** —— 在那之前，`confine` 那 387 行都只是纸面。
**V3 跑通，"远程管家"的骨架就成立了**：一个没人看着的进程，跑到需要决定的地方，
在你手机上问你，你点一下，它继续。

V0 和 V1 可以立刻做。V2 需要一台 Linux。V4 需要 AGX 在手边。
